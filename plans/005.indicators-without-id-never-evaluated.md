# 005 — Plan

Spec: [`specs/005.indicators-without-id-never-evaluated.md`](../specs/005.indicators-without-id-never-evaluated.md)

## Solution

Two changes, one per cause in §3.

### A — `currentState` reads the `ignore` flag (§3.a → §1.1, §1.2)

`src/dca/strategy/ti/index.ts:1016`. Registration already answers "is this a
helper child?" — it sets `ignore: true` on the MA child (`:572`) and the XO
child (`:607`) and `ignore: false` on everything the user configured (`:543`,
`:628`). The same file already filters on `!i.ignore` in the six
`IndicatorAction` buckets at `:1839-1870`. Use it here too and delete the id
string test, which is a second, broken implementation of the same question.

```ts
const currentState = [...Strategy.indicators].filter(
  (i) => !i.ignore && i.data.length > 0 && i.symbol === nextBar.symbol,
)
```

This also removes the always-truthy `` `${i.settings.xoUUID}@${nextBar.symbol}` ``
operand (§4.2) rather than "mirroring" it into a real comparison — the flag
covers both children, so there is nothing left to compare.

Helper children stay in `Strategy.indicators`, so the crossing lookups at
`:1481` / `:1522` (`Strategy.indicators.find(ii => ii.id === ...)`) are
unaffected; they were never reading `currentState`.

### B — every indicator reaches the engine with an id (§3.b → §1.3)

`src/helper/utils.ts` gains `withIndicatorIds(settings)`: it returns the same
object when every indicator already has a `uuid` (the dashboard case — no
allocation, no behaviour change), and otherwise fills the gaps with a
deterministic `indicator-<index>`, skipping any value an explicit `uuid`
already uses.

`src/dca/index.ts` — `DCABacktesting`'s constructor runs its input through it
once, before `settings` is handed to `super()`, `getStrategyBySettings()` and
`CombinedStrategy`.

Why the constructor and not the registration site: it is the single choke point
for the whole DCA engine (`getStrategyBySettings` is called only from
`src/dca/index.ts:75`; `HedgeBacktesting` builds both legs with
`new DCABacktesting(...)`; grid has no indicators), and it fixes `settings.uuid`
itself rather than only the registration key. That matters for §1.4:
`getDynamicLevels` emits `i.id.split('@')[0]` and `dcaBotFunctions` looks the
value up again as `indicator.uuid`, so the two must stay equal. Patching only
the registration id would silently break dynamic AR/TP/SL for id-less
indicators. It also fixes `uuid: ""`, which today makes `getDynamicLevels` bail
out entirely via its `if (!id) continue` + length check.

Deterministic, not `v4()`: indicator ids surface in the result through
`dynamicAr: DynamicArPrices[]`, and the engine runs both server-side (main-app
:7515) and client-side in both dashboards — the two must agree.

### JIT-legacy tier

**Tier 0 for `checkIndicators`.** Change A deletes a predicate and substitutes
an existing flag inside a 800-line method; the method is not otherwise on the
causal path and extracting it would be a rewrite of the engine's hot loop, not
a fix. Change B is a **Tier 2** pure function (no I/O, no imports beyond a
type) with its own unit test — the lowest tier that removes the smell, per the
runbook.

## Blast radius

1. **Other call sites of the thing being changed.** `currentState` is local to
   `checkIndicators`. The `ignore` flag is read in six other places in the same
   file, all with the same `!i.ignore` polarity — this change makes the seventh
   consistent with them. `withIndicatorIds` is new; its only caller is the
   `DCABacktesting` constructor.
2. **`core/` submodule.** None — `backtester` has no `.gitmodules`.
3. **Contracts this repo owns** (`CLAUDE.md` → "Coupling"). The engine is
   consumed by main-app's backtest worker (:7515) **and** client-side by both
   dashboards; results must stay identical between them. Neither change is
   environment-dependent (no clock, no randomness, no I/O), so server↔client
   parity holds. `DCABacktestingInput` / the result types are untouched.
   Danger-List #13 applies: **backtest results change for id-less indicators**,
   which is the point — such bots returned zero deals. Results for bots built in
   the dashboard (every indicator has a real `uuid`) are unchanged; the
   regression table below is the evidence.
4. **Other tests on this path.** The whole 21-test mocha suite must stay green,
   plus the ad-hoc regression table (MA crossing, XO crossing, XO-in-a-group,
   plain baselines) captured before the change.
