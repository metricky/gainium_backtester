# 002 — Grid force-close (`stopAndSell`) emits no transaction on futures

## Solution

Fix the root cause named in spec §3.1: make the futures `stopAndSell`
close go through the same transaction ledger as every other fill.

## Build order

1. **Tier 1 extraction** (JIT runbook): lift the transaction-record
   construction out of the tail of `createTransaction()` into a new
   private `pushTransaction(draft)` — it builds the
   `BacktestingTransaction`, advances `cummulativeProfit` and
   `transactionIndex`, and pushes. Profit *accrual*
   (`totalProfit`/`totalProfitUsd`/`freeTotalProfit`) stays with the
   callers, which already own it and compute their USD rate
   differently (`usdRate` vs `usdRateQuote * (coinm ? price : 1)`).
   No behaviour change — same fields, same order, same rounding.
2. `createTransaction()` calls `pushTransaction(...)` with exactly the
   values it computes today.
3. `closeBot()`'s futures branch calls `pushTransaction(...)` for the
   position close, using the P&L it already computed, matched against
   the position entry price the way the existing directional-futures
   branch of `createTransaction` does (`matchQty = profitBase ? (price *
   qty) / (entryPrice || price) : qty`, `matchedPrice = entryPrice`).
   Side is the side that closes the position (LONG → SELL). Guarded on
   `qty > 0 && entryPrice > 0` per spec §4.2.
4. Accrual in `closeBot` is untouched, so `profitTotal`,
   `profitTotalUsd`, `currentBalances`, `valueChange` and
   `freeProfitTotal` all keep their current values — only the ledger
   gains the missing row.

## Contract decisions the spec left open

- **Row `profit`** = the P&L `closeBot` already accrued, no close fee
  (spec §3.4) — so `sum(transaction.profit) === profitTotal`.
- **Row `profitUsd`** = `profit * (coinm ? price : 1) * usdRateQuote`,
  i.e. the same conversion `closeBot` uses for `totalProfitUsd`, so the
  USD ledger reconciles too (and `ratios.profitByPeriod`, which sums
  `transaction.profitUsd`, finally sees the closing loss).
- **Row `freeProfit`** = the same P&L (there is no grid-matched "free"
  variant of a force close), but `freeTotalProfit` is *not* accrued
  (spec §3.3). Nothing downstream sums `transaction.freeProfit`
  (checked across main-app, main-dash-redesign, main-dash).
- **Order ids**: `executor` = a generated id via
  `botFunctions.utils.id(20)` (the helper the file already uses for
  history lines); the matched leg is `'position price'`, the marker the
  existing futures-directional branch already uses.
- **`numerical.all/buy/sell`** are derived from `this.transactions` in
  `returnResult()` — they pick the new row up with no code change, which
  is correct: the force close is a real order.

## Blast radius

1. **Other call sites.** `createTransaction` is called only from
   `processBar` (2 sites, same file). `closeBot` only from `processBar`.
   `pushTransaction` is new. `checkPosition` deliberately untouched
   (spec §4.1).
2. **`core/` submodule.** None in this repo.
3. **CLAUDE.md contracts.** Danger List #13 — this engine runs
   server-side (main-app `:7515` backtest worker) *and* client-side in
   both dashboards, from the same published package, so both sides move
   together; no input/result **type** changes (`BacktestingTransaction`
   is unchanged, one more element in an existing array). Downstream
   effects, all intended: the V2 backtest Transactions table
   (`GridBacktestTransactionsTab.tsx`) shows one more row;
   `numerical.*` counts +1; `ratios.sharpe/sortino` improve in accuracy
   because `profitByPeriod` now includes the closing loss; the paper bot
   main-app mirrors from a backtest
   (`main-app/src/backtest/process/main.ts`) gains the same row.
   `profitTotal`, `valueChange`, `freeProfitTotal` are byte-identical.
4. **Other tests.** `test/placeholder.spec.ts` only; both must stay
   green.
