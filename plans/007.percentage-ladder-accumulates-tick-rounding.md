# 007 — plan

## Build order

1. `backtester` — `dcaBotFunctions.createOrders`: add an unrounded running
   level (`percentageLevel`) before the ladder loop. Each iteration subtracts
   `dir × gridStep × stepVal` from it and rounds only that level (§1.1).
   Widen the `i > 1` separation guard: for non-indicator, non-custom ladders,
   a level at or behind the previous one is pushed one tick past it (§1.2).
2. `main-app-sh` — the same change in `dcaHelper.createInitialDealOrders`,
   plus `orders.length > 0` on the widened guard: that copy reads a missing
   previous order as price 0, which would otherwise fire it.
3. `main-dash-sh` — the same change in `createDCAOrders` only (not
   `createComboOrders`).
4. Version and CHANGELOG entries in all three. Consumers pin
   `@gainium/backtester` by git ref, so the server-side backtest and the
   dashboards pick the engine change up with their next bump.

JIT tier: none. This is a three-line arithmetic change inside the existing
loop. Extracting a shared ladder function would mean a new cross-repo
package, which is out of proportion to the fix.

## Blast Radius

1. **Call sites.** `createInitialDealOrders` has 15 callers in `dcaHelper.ts`
   (deal start, settings update, restore). All of them build ladders; open
   deals keep their persisted `initialOrders` until something rebuilds them.
   The combo copies are deliberately untouched (§1.3).
2. **`core/`.** Both `main-app-sh` and `main-dash-sh` are shared submodules.
   No types, schema, event or queue shape changes: only the numeric prices a
   ladder produces.
3. **Contracts.** Danger List #13 (backtester parity): all three copies change
   together, and parity is verified before and after on 11 configurations.
4. **Other tests.** In the main-app core suite,
   `nanLadderRefusal.harness.spec.ts` pinned level 30 of a 1e-6-tick ladder
   from the drifted build (0.001832). It is re-pinned to the configured level
   (0.001828, qty 74307). Everything else stays green.
