# 004 — plan

Spec: [`../specs/004.lot-step-rounding-inflates-order-qty.md`](../specs/004.lot-step-rounding-inflates-order-qty.md)

## Solution

Add one helper next to the one it corrects, and call it from the four sites.

### `MathHelper.gridRemainder(a, b)` — `src/helper/math.ts`

Answers "how far is `a` above the `b` grid", reading a value that is already a
whole number of steps as `0`, and delegating to the existing
`MathHelper.remainder()` for a genuinely off-grid value.

This is deliberately a *second* method rather than a change to `remainder()`.
`remainder()` is also used as an exact modulo on loop counters
(`grid/strategy/index.ts:320`, `dca/strategy/combined.ts:227`,
`hedge/index.ts:440`) and on multi-TP quantities; widening its contract would
silently move results at six call sites the spec does not cover. §5 records
that residue.

Tolerance, per spec §3.1 — scale-aware, reusing the class's existing `eps`
rather than introducing a second magic constant:

```
tolerance = min(1e-3, max(eps, |a/b| * eps))
```

- floored at `eps` so small ratios behave exactly as the repo's other
  tolerance helpers (`isZero`, `gt`, `lt`) do;
- scaled by `|a/b|` because that is how the float noise in the division
  actually grows (spec §3.1);
- capped at `1e-3` of a step so it can never swallow a real remainder — the
  smallest gap measured on a genuinely off-grid quantity is `0.2` of a step.

The round-up expression itself (`qty - mod + step`, ceil at precision) is left
untouched: with `mod === 0` it no longer runs, and for a real remainder it is
unchanged behaviour.

## Blast Radius

1. **Other call sites of the pattern.** `grep -n "remainder(\|% symbol.baseAsset.step" src/` →
   14 hits. Four are changed (above). The other ten keep `remainder()`:
   `dcaBotFunctions.ts:396,915`, `comboBotFunctions.ts:508`,
   `dca/strategy/main.ts:5422,5503` (multi-TP quantities) and
   `hedge/index.ts:440`, `dca/strategy/combined.ts:227`,
   `grid/strategy/index.ts:320` (integer loop counters — unaffected by float
   noise). `gridRemainder` is additive, so none of them change.
2. **`core/` submodule.** None — `backtester` has no `.gitmodules`.
3. **Cross-service contracts** (repo `CLAUDE.md` → *Coupling*). The engine is
   run server-side by main-app's backtest worker (:7515) and client-side by
   both dashboards, from the same published build, so they cannot diverge.
   No `DCABacktestingInput` / `GRIDBacktestingInput` / result type is touched;
   no GraphQL, queue, socket or DB shape is touched. Engine *math* does change
   — that is the fix — and it changes identically in all three runners once the
   consumers bump the pin.
4. **Existing tests that must stay green.** `test/grid-force-close-transaction.spec.ts`
   and `test/grid-tpsl-priceReached.spec.ts` both drive the grid engine through
   `createGridOrders`, i.e. through the changed `botUtils.ts:577` line.

**`comboBotFunctions.ts:198` has no dedicated suite test.** Its base quantity
is reshaped downstream by the minigrid split, so there is no end-to-end

the byte-identical expression to `dcaBotFunctions.ts:316`, it shares the unit
tests of the helper, and it was verified by the §2.3 instrumentation: 55 of
300 inflated at step `0.001` before, 0 after. Recorded here rather than
covered by a vacuous assertion.

## §5 Out of scope, recorded

`MathHelper.remainder()` itself still misreads an aligned quantity (12.5 % at
step `0.001`, 50 % at step `1e-8`). The five multi-TP call sites listed in
Blast Radius §1 therefore carry the same latent defect on a take-profit
quantity. Not fixed here: it would move a second, independent class of
backtest results, and it has not been reproduced end-to-end as a user-visible
symptom.
