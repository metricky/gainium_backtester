# 003 — grid `priceReached` stop-loss is never evaluated when a take-profit is also set

Bug spec (Part 0 / bug template).

## §1 Definition

`Strategy.tpSl(lastPrice)` in `src/grid/strategy/index.ts` decides, once per
price point, whether a grid bot must stop on take-profit or on stop-loss.
The live bot engine's equivalent (`main-app/core/src/bot/helper.ts`, `tpSl()`)
is the oracle for correct behaviour.

### §1.1 Both rules must be evaluated on every price point

A grid bot may have a `priceReached` take-profit **and** a `priceReached`
stop-loss configured at the same time (the dashboard exposes them as two
independent switches, `tpSl` and `sl`).

- **Expected:** on every price point, the take-profit rule is checked and, if
  it does not trigger, the stop-loss rule is checked too. TP keeps priority
  when both would trigger on the same price point.
- **Actual:** the four `priceReached` branches are one `if / else if` chain.
  For a LONG grid the take-profit branch's *guard* matches (the TP is
  configured), so the chain is consumed there; when the inner price
  comparison does not trigger, control leaves the whole chain and the
  stop-loss branch is never reached. The stop-loss is dead for the entire
  backtest.

### §1.2 A short grid's stop-loss triggers when price rises

For a SHORT grid the adverse direction is up, so `slLowPrice` is above the
position.

- **Expected:** `lastPrice >= slLowPrice` triggers the stop-loss (this is what
  the live engine does).
- **Actual:** the backtester compares `lastPrice <= slLowPrice`, i.e. it
  triggers in the *profitable* direction — normally on the very first bar.

§1.2 is currently masked by §1.1 for any short grid that also has a
`priceReached` take-profit (the chain never reaches the short SL branch), so
the two must be fixed together: fixing §1.1 alone would expose §1.2 to every
short grid backtest.

### §1.3 Mixed conditions

`tpSlCondition` and `slCondition` are independent; a bot may run a
`priceReached` TP with a `valueChanged` SL. The same chain makes the
`valueChanged` block unreachable in that case. Expected: evaluated, as the
live engine does.

### §1.4 Out of scope

Result shape, totals and the transaction ledger are unchanged — this spec
only changes *whether/when* `closeBot` is reached. A run that already closed
closes identically.

## §2 Evidence

Engine driven directly (`ts-node`, reporter's exported settings from
`backtest-HEMIUSDT.json`: LONG, `tpSl`+`sl` both true, both `priceReached`,
`tpTopPrice` 0.005392, `slLowPrice` 0.004115), with `closeBot` and
`checkPosition` instrumented to record every close event:

| run | bars | close event |
|---|---|---|
| LONG, TP+SL both set, price breaks down to 0.00404 | 19 | **NONE — bot ran to the end**, `botClosed:false`, 33 transactions |
| identical bars, `tpSl:false` (TP removed) | 19 | `closeBot(sl) @ 0.0041, bar 16` |
| SHORT, SL only at 0.005392, price starts 0.004755 and rises | 9 | `closeBot(sl) @ 0.004855, bar 1` — fired below the SL price, on bar 1 |

Row 1 vs row 2 is the proof for §1.1: the same price path that closes on SL
with the TP switch off does not close at all with it on. Row 3 is the proof
for §1.2. Liquidation was excluded as a confounder by running rows 1–2 on
`futures:false, leverage:1`.

## §3 Assumption (hypothesis)

The root cause is the `else if` chaining of the four `priceReached` guards
(and of the trailing `valueChanged` block) in `tpSl()`
(`src/grid/strategy/index.ts:1229-1265`), plus the inverted comparison
`lastPrice <= +slLowPrice` in the short stop-loss branch. Making the blocks
independent `if`s and flipping the short comparison to `>=` — i.e. mirroring
`main-app/core/src/bot/helper.ts:4057-4100` exactly — restores both.

Not the cause: `closeBot`, `checkPosition` (liquidation), grid construction,
or the transaction ledger. Those were all exercised in the evidence runs and
behave correctly once `tpSl()` returns the right verdict.
