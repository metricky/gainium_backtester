# 002 — Grid force-close (`stopAndSell`) emits no transaction on futures

## §1. Definition

A grid bot with `tpSl`/`sl` set to `priceReached` and
`tpSlAction`/`slAction` = `stopAndSell` stops and force-closes its open
position when price leaves the grid range.

- **§1.1 Expected.** That force close is a real trade — it closes the
  whole position at the trigger price and realizes a P&L (normally a
  loss, since the grid is stopped on the wrong side of the range). It
  must appear in the backtest Transactions list, so the list reconciles
  with the reported totals: `sum(transaction.profit) === profitTotal`.
- **§1.2 Actual (futures).** No transaction row is produced for the
  force close. Its P&L is added straight to the running total, so the
  Transactions list ends on the last *grid* fill and
  `sum(transaction.profit) !== profitTotal` — the list overstates the
  result by exactly the (hidden) closing loss.
- **§1.3 Actual (spot) — NOT part of this defect.** On spot the same
  branch realizes nothing into the profit accumulator; it converts the
  leftover base inventory into quote in `currentBalancesByAsset`. The
  `sum(transaction.profit) === profitTotal` invariant already holds
  there. See §3.2.

## §2. Evidence

- **§2.1 Reporter's artifact** (`backtest-HEMIUSDT.json`, binanceUsdm
  futures, geometric 20 levels, `tpSlAction: stopAndSell`,
  `tpTopPrice 0.005392`): 47 transactions, `sum(transaction.profit) =
  4.8906`, `financial.profitTotal = 4.6`, `valueChange = 4.6`. The
  ledger is short by 0.2906 quote — the unrecorded closing loss. The
  last row (index 46) is a plain grid sell at 0.005322 whose profit is
  the fee alone; nothing follows it.
- **§2.2 Runtime evidence — the branch ran and pushed nothing.**
  Replaying the reporter's exact settings through the real engine with
  a probe wrapped around `Strategy.prototype.closeBot` /
  `checkPosition` / `createTransaction`:

  ```
  [probe] closeBot() totalProfit 1.958811 -> -4.960472 (delta -6.919283),
          transactions 28 -> 28, args=[0.0055,1782951600000,"tp"]
  sum(tx.profit) = 1.9594   financial.profitTotal = -5
  ```

  `closeBot(price, time, "tp")` executed, moved the profit accumulator
  by the full close P&L and left `this.transactions` untouched.
  `checkPosition()` (liquidation) never fired, so the delta is
  attributable to the force close and to nothing else.
- **§2.3 Same replay with `futures: false`** — `[probe] closeBot()
  totalProfit 10.124835 -> 10.124835 (delta 0.000000)`, and
  `sum(tx.profit) 10.1248` vs `profitTotal 10.1`: the spot branch
  realizes no P&L, confirming §1.3.
- **§2.4 Origin — latent.** `git blame -L1283,1343
  src/grid/strategy/index.ts` → the whole `closeBot` body is `a09f382`
  (2023‑05‑15, the repo's initial commit); the only later touch,
  `d23f1a1` (2025‑07‑02), is a Prettier reflow. `git log -S
  "this.botClosedAndSell = true"` returns `a09f382` alone. The engine
  has never ledgered this close.

## §3. Assumption (hypothesis)

- **§3.1** Root cause: `closeBot()`'s futures branch
  (`src/grid/strategy/index.ts`) computes the close P&L and accrues it
  into `totalProfit`/`totalProfitUsd` directly, bypassing
  `createTransaction()` — the only place a `BacktestingTransaction` is
  ever pushed. Emitting a transaction row for the close, carrying the
  P&L already computed there, restores §1.1 without changing any total.
- **§3.2** The spot branch is *not* the same defect and must not get a
  synthetic row: it accrues nothing, so a row carrying a profit would
  double-count and would break an invariant that currently holds
  (§2.3). Its effect is already visible in `valueChange`.
- **§3.3** `freeProfitTotal` (`freeTotalProfit`) is deliberately left
  alone. It is a separate grid-matching metric that also feeds
  `currentBalancesByAsset`, `breakevenPrice()` and, downstream,
  `profit.freeTotal` on the paper bot main-app creates from a backtest
  (`main-dash-redesign/core/src/types/gridBot.ts`). Accruing the close
  into it would change a stored, displayed number that the report does
  not concern.
- **§3.4** No fee is charged on the force close today; the row must
  carry exactly the P&L that was accrued, or `sum(transaction.profit)`
  would still not equal `profitTotal`. Charging a close fee is a
  separate math change, out of scope.

## §4. Out of scope (named, not fixed)

- **§4.1** `checkPosition()` (liquidation, same file) accrues
  `-(entryPrice*qty)/leverage` with no transaction row either — the
  same class of gap, but a different event with no meaningful
  buy/sell price pair. Not the reported symptom.
- **§4.2** With a flat position (`qty === 0`, `entryPrice === 0`) the
  existing `diff` computation is `Infinity` and `profit` is `NaN`. The
  fix must not emit a row in that case; repairing the pre-existing NaN
  is out of scope.
