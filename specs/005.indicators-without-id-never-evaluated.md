# 005 — A DCA indicator that carries no id is never evaluated

Bug spec (Part 0 of `gainium-dev-flow`).

## §1 Definition

### §1.1 Every user indicator must be evaluated, id or no id

`DCABacktestingInput.settings.indicators[]` carries a `uuid`. The dashboard
always assigns one; the GraphQL bot API does not require one, so a bot built
through `createDCABot` can reach the engine with `uuid: null`.

**Expected.** The presence or absence of `uuid` changes nothing about whether an
indicator's condition is evaluated. Two runs over the same candles with the same
rules must produce the same deals whether or not the indicators carry ids.

**Actual.** An indicator without an id is silently dropped from the per-bar
evaluation set. Its status never becomes true, so every group containing it stays
false and the bot never opens a deal. The backtest finishes with no deals and no
error — it looks like a strategy that simply never trades.

### §1.2 Only helper children may be excluded from the evaluation set

The engine registers two kinds of entry in `Strategy.indicators`: the user's own
indicators (`ignore: false`) and the *helper children* it synthesises for the
second leg of an MA crossing (`${maUUID}@pair`) and of an XO crossing
(`${xoUUID}@pair`), both registered with `ignore: true`.

**Expected.** The per-bar evaluation set (`currentState`) contains exactly the
entries with `ignore === false`. Helper children are read by id where the
crossing needs them (`ti/index.ts:1481`, `:1522`) and are not evaluated as
indicators in their own right.

**Actual.** Membership is decided by comparing the entry's id string against the
helper id it *would* have had. Any entry whose id happens to equal
`` `${settings.maUUID}@${symbol}` `` is dropped, whether or not it is a helper. The
XO half of the test is not a comparison at all.

### §1.3 An indicator's id must identify exactly one indicator

**Expected.** Two different indicators are two different entries: updating one
never writes over the other.

**Actual.** Several places key an indicator by its registration id —
`updateIndicatorData` (`ti/index.ts:928`), the status write-back
(`ti/index.ts:1823`) and the `nextBarTime` map (`ti/index.ts:852`). Two
indicators that both arrive without a `uuid` register under the same id
`` `null@${pair}` `` and overwrite each other, so an AND of two id-less
indicators does not mean AND.

### §1.4 `getDynamicLevels` must keep producing values for id-less indicators

`getDynamicLevels` (`dca/strategy/main.ts:1609`) derives a dynamic-AR id as
`i.id.split('@')[0]` and `dcaBotFunctions` looks it up again as
`indicator.uuid`. Whatever §1.3 does to make ids unique must keep those two
sides equal, or dynamic AR/TP/SL levels break for id-less indicators.

## §2 Evidence

Repro harness `/root/claus-810/` (reporter's `repro-indicators-without-id.cjs`,
with the candles cached): long BTC-USDT bot, Binance USD-M paper, 1h,
2025-09-01 → 2026-08-31, exit +2 %, against `master` @ `de258db`.

```
RSI<35 AND RSI>20, with uuids                   6 deals
same two, uuid = null                           0 deals
RSI>20 alone, with uuid                         8 deals
RSI>20 alone, uuid = null                       0 deals   <- nothing to collide with
RSI>20 alone, uuid="q" maUUID="q"               0 deals   <- id is NOT null, still dropped
RSI>20 alone, uuid="" (empty string)            8 deals   <- "" != "null", so it survives
```

The last two rows are what pins the mechanism: it is not null-handling. It is
string equality between the entry's id and the helper id.

**Runtime probe** (temporary `console`-counter compiled into
`dist/src/dca/strategy/ti/index.js`, counting per bar over the same run):

```
RSI>20 alone, with uuid     -> 8 deals
    rsi-high@BTC-USDT  ignore=false  droppedByMaUUIDstring=false  bars=8736
RSI>20 alone, uuid = null   -> 0 deals
    null@BTC-USDT      ignore=false  droppedByMaUUIDstring=true   bars=8736
RSI>20 alone, uuid="q" maUUID="q" -> 0 deals
    q@BTC-USDT         ignore=false  droppedByMaUUIDstring=true   bars=8736
```

So the indicator **is** registered, **is** fed data on all 8736 evaluated bars,
and **is** flagged `ignore=false` — i.e. the engine already knows it is a real
user indicator — and it is still dropped on every single bar. This distinguishes
"never ran" from "ran and was filtered": it ran, and the id test filtered it.

## §3 Assumption (hypothesis, not fact)

Two independent causes, both required:

**§3.a** `ti/index.ts:1016-1021` re-derives "is this a helper child?" from an id
string instead of reading the `ignore` flag that registration already set for
exactly this purpose (and that the same file already uses six times, lines
1839-1870):

```ts
const currentState = [...Strategy.indicators].filter(
  (i) =>
    i.id !== `${i.settings.maUUID}@${nextBar.symbol}` &&
    `${i.settings.xoUUID}@${nextBar.symbol}` &&   // a non-empty string: always true
    i.data.length > 0 &&
    i.symbol === nextBar.symbol,
)
```

For an ordinary indicator `maUUID` is `null`, so the helper id is the literal
string `null@PAIR`; an indicator with `uuid: null` registers under exactly that
id and matches its own exclusion test. The same collision happens for any
indicator whose own `uuid` equals its `maUUID`.

**§3.b** Registration ids are not unique when `uuid` is absent, so §1.3's
id-keyed writes collide.

Fixing §3.a alone leaves the two-indicator AND case wrong (§1.3); fixing §3.b
alone leaves the `uuid === maUUID` collision wrong (§1.2). Both are needed.

## §4 Open questions

- §4.1 Whether `changeDCABot`/`createDCABot` in main-app should reject or fill a
  missing indicator `uuid` at write time. Out of scope here — the engine must be
  correct for the input it is given either way, and the live bot path goes
  through main-app's own indicator service, which this spec has not read.
- §4.2 The always-truthy `xoUUID` operand means XO helper children are currently
  evaluated as if they were user indicators. Their status is never read (every
  downstream consumer filters on `!i.ignore`), so this is believed to be dead
  work rather than wrong results — but it is a real behaviour change and §1.2
  ends it, so it must be regression-checked, not assumed.
