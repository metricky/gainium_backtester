# 006 — a grid force close on a flat position makes every reported figure NaN

Bug spec (Part 0 / bug template).

## §1 Definition

`Strategy.closeBot(price, time, action)` in `src/grid/strategy/index.ts`
force-closes the remaining futures position when a grid bot stops on a
`stopAndSell` take-profit or stop-loss. It computes that close's P&L itself,
from the position's entry price.

### §1.1 A close with no open position contributes no profit

A grid bot can be stopped on a bar where its net position is flat. Two ways in:

- the stop triggers before any grid order fills (a `priceReached` trigger on
  the wrong side of the start price fires on bar 1);
- a neutral grid passes through `qty 0` whenever its open legs are all matched,
  and the stop lands on one of those bars.

In both cases `position` is `{ qty: 0, entryPrice: 0 }`.

- **Expected:** the force close contributes `0` to `totalProfit`. Every other
  figure — the transactions already booked, `profitTotal`, `valueChange`,
  `currentBalances` — is whatever the run earned up to that bar.
- **Actual:** `diff` divides by `current.entryPrice`, which is `0`, giving
  `Infinity`; `profit` is then `0 * 0 * Infinity` = `NaN`. `totalProfit += NaN`
  makes `totalProfit`, `totalProfitUsd` and `currentBalances` NaN for the rest
  of the run. `returnResult()` rounds those to `0`, so the backtest reports
  `profitTotal 0`, `valueChange 0` and `currentBalances 0` with no error.

The transaction rows themselves survive — the ledger write added in spec 002 is
already guarded on `qty > 0 && entryPrice > 0`. Only the arithmetic above that
guard is unguarded, so the rows and the totals disagree: a run with four booked
transactions and a real profit reports zero.

### §1.2 The empty-run case

When the trigger fires on bar 1, there are no transactions to disagree with,
and the whole result is zeros: no orders, no transactions, a single equity
point, `currentBalances 0` against an `initialBalances` of the full budget.
That reads as "the backtest produced nothing" rather than "the bot stopped
immediately on its take-profit", which is what actually happened.

### §1.3 Out of scope

*Whether* the bot should stop is unchanged — this spec does not touch `tpSl()`
(spec 003) or the trigger comparisons. A configuration whose take-profit sits
below the start price still stops on bar 1; it just reports the budget it never
spent instead of `0`. The ledger, the transaction shape and the spot close path
are likewise unchanged.

## §2 Evidence

Engine driven directly (`ts-node`), settings verbatim from the reporter's
exported `backtest-ARKUSDT.json` (binanceUsdm futures grid, geometric, 21
levels, range 0.12231–0.20859, `tpSl`+`sl` both `priceReached`, both
`stopAndSell`, LONG / NEUTRAL).

| run | close | position at close | `totalProfit` | reported |
|---|---|---|---|---|
| reporter's settings (`tpTopPrice` 0.12231 = the range's **low**, start 0.1343) | `tp` @ 0.1338, bar 1 | `qty 0, entryPrice 0` | **NaN** | `profitTotal 0`, `currentBalances 0` against `initialBalances 288.4`, 0 transactions |
| same grid, `tpTopPrice 0.1375`, price dips and recovers so the legs all match before the stop | `tp` @ 0.138, bar 14 | `qty 0, entryPrice 0` | **NaN** | `profitTotal 0`, `valueChange 0`, `currentBalances 0` — with **4 booked transactions and +0.5556 real profit** |
| same grid, stop lands while the position is open | `tp` @ 0.1455, bar 18 | `qty 168.4, entryPrice 0.14073` | −0.2571 | reconciles; 7 transactions incl. the force-close row |

Row 2 is the load-bearing one: the run is ordinary and correct up to the stop,
and the reported result is wiped. Row 3 is the unaffected path, included to
show the fix must not move it.

## §3 Assumption (hypothesis)

The root cause is the unguarded division by `current.entryPrice` in the futures
`stopAndSell` branch of `closeBot()` (`src/grid/strategy/index.ts:1341-1348`).
Computing `diff` and `profit` as `0` when the position is flat — the condition
the ledger write below them already tests — confines the close to what it
actually is on that bar: nothing.

Not the cause: `tpSl()`, the trigger comparisons, `pushTransaction`,
`checkPosition` (liquidation), or `returnResult`'s rounding. `returnResult`
turning NaN into `0` is what hides the fault, but a NaN should never reach it.
