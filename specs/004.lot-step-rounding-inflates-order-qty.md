# 004 — an order quantity already on the lot grid is rounded up by a whole lot

Bug spec (Part 0 / bug template).

## §1 Definition

Four places in the order builders round a quantity **up** to the symbol's lot
step so the venue will accept it:

| site | expression |
|---|---|
| `src/helper/dcaBotFunctions.ts:316` (DCA base order) | `baseOrder.qty % symbol.baseAsset.step` |
| `src/helper/dcaBotFunctions.ts:716` (DCA safety order) | `qty % symbol.baseAsset.step` |
| `src/helper/comboBotFunctions.ts:198` (combo base order) | `baseOrder.qty % symbol.baseAsset.step` |
| `src/helper/botUtils.ts:577-579` (grid order) | `tradesBacktest ? gridQty % step : this.math.remainder(gridQty, step)` |

Each reads the remainder, and if it is non-zero replaces the quantity with
`round(qty - mod + step, precision, false, /* up */ true)`.

### §1.1 A quantity that is already a whole number of steps must be left alone

- **Expected:** a quantity that is already `k × step` has remainder 0, the
  round-up does not fire, and the order is sized at the budget the user set.
  The live bot engine is the oracle here: `main-app-sh`'s `dcaHelper.ts`
  computes the same remainder with Big.js (`new Big(qty).mod(step)`) and does
  not fire.
- **Actual:** in binary floating point neither `%` nor `MathHelper.remainder()`
  reads such a quantity as 0, so the round-up fires on a quantity that needs no
  rounding and `qty - mod + step` lands a hair above `qty`. The ceil at the
  step's precision turns that hair into a **whole extra lot**.

### §1.2 A genuinely off-grid quantity must still round up

A quantity that is not a whole number of steps (reachable when the step is not
a power of ten — `0.005`, `0.002`, `2.5` — because the working precision is
coarser than the grid) must still be raised to the next step.

### §2.3 The safety-order and combo sites

Both order builders instrumented at the round-up, 300 prices per step, DCA
with three safety orders:

```
step=0.001   dcaBotFunctions.ts:716  900 passes, all aligned, 501 gained a whole lot
step=0.001   comboBotFunctions.ts:198 300 passes, all aligned,  55 gained a whole lot
step=0.01    dcaBotFunctions.ts:716  900 passes, all aligned, 321 gained a whole lot

```

Every single quantity reaching these sites was already a whole number of
steps — `precision` is derived from the step
(`BotUtils.getBaseAssetPrecision`), so for a power-of-ten step the quantity
cannot be off the grid and the round-up is *always* spurious there.

### §2.4 Why the round-up turns a hair into a lot

```
0.145 % 0.001                 -> 0.000999999999999987     (not 0)
0.145 - 0.000999999999999987  -> 0.14400000000000002
          + 0.001             -> 0.14500000000000002
round(…, 3, up)               -> 0.146
```

## §3 Assumption (hypothesis)

The root cause is the **remainder test**, not the round-up. Neither `%` nor
`MathHelper.remainder()` can decide "is this value a whole number of steps"
for binary floats. Supplying a remainder function that answers that question
correctly fixes all four sites without touching the round-up itself.

### §3.1 A fixed absolute tolerance does not answer it either

The reporter's attached patch proposes `|a/b − round(a/b)| < 1e-9`. That is
right in shape and wrong in scale: the noise in `a / b` grows with the ratio,
so a constant tolerance runs out. Measured over 469 720 aligned quantities
spanning steps `1e-8 … 2.5` and ratios up to `1e9`:

```
                        misses on aligned qty      false zeros on off-grid qty
  abs 1e-9 (reporter)      41827 / 469720                 0 / 144868
  abs 1e-10 (repo eps)     69448 / 469720                 0 / 144868
  scale-aware + capped         0 / 469720                 0 / 144868
```

Concretely, with the fixed `1e-9` a `0.001`-step quantity of `67112.487` is
still misread, and 15.6 % of `1e-8`-step quantities below 10 units are. The
tolerance must scale with `|a/b|` — floored at the helper's existing `eps` and
capped well below the smallest gap a genuinely off-grid quantity shows
(measured minimum: 0.2 of a step, i.e. eight orders of magnitude of headroom).

## §4 Blast radius

`@gainium/backtester` is the shared engine: main-app's backtest worker (:7515)
and both dashboards' in-browser backtest run the same code, so server and
client stay identical only because they run the same build. The change is
confined to order *sizing* inside this library; no input/result type, no
GraphQL field, no queue payload, no socket event changes. Live trading is not
affected — the live engine already rounds correctly.

Existing backtest results move: wherever the defect used to fire, the backtest
now opens the position the budget allows, i.e. **slightly smaller** than
before.
